                         YANG Schema Comparison
              draft-ietf-netmod-yang-schema-comparison-10

Abstract

   This document specifies an algorithm with two input variants for
   comparing revisions of a YANG schema to determine the scope of
   changes and produce a list of the changes between the revisions.  The
   output of the algorithm can be used to help select an appropriate
   YANG semantic version number for a new YANG Module revision.  It also
   specifies a YANG module for YANG-structured output of these
   algorithms, that can be easily consumed in a machine-readable way.

1.  Introduction

   This document defines a common algorithm for comparing two revisions
   of a YANG schema.  As input, there can be two types of YANG schema
   representations: single locally resolved YANG modules or fully
   resolved set of YANG modules (on-the-wire schema).  The algorithm
   output for each of these representations serves a different purpose.
   It can help YANG authors with assigning the correct semantic version
   of a module based on [I-D.ietf-netmod-yang-semver] or tools
   processing YANG instance data can use it to learn about the exact
   data changes, respectively.

   The algorithm operates in a straightforward way traversing all the
   statements and their substatements in both the old and new module
   representations collecting identified changes.  These are then
   reported in a concise output with information about the overall
   backwards compatibility between the two modules.  Exact output format
   is out of scope for this document but Appendix A includes an example
   of a YANG module whose YANG data can represent all the possible
   changes and so a complete output of this algorithm.

   Every change is classified as editorial, backwards-compatible, or
   non-backwards-compatible.  This conformance is decided based on rules
   found in other documents, specifically [RFC7950],
   [I-D.ietf-netmod-yang-module-versioning], and
   [I-D.ietf-netmod-yang-semver].  For older YANG 1.0 modules, the rules
   in [RFC6020] apply instead.

2.  Terminology and Conventions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in BCP
   14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   This document makes use of the following terminology introduced in
   the YANG 1.1 Data Modeling Language [RFC7950]:

   *  module

   *  schema node

   *  data node

   *  data definition statement

   In addition, this document uses the following terminology:



Vaško, et al.             Expires 25 April 2027                 [Page 3]

Internet-Draft           YANG Schema Comparison             October 2026


   *  locally resolved module: A parsed YANG module with all its
      submodules and local references resolved.

   *  fully resolved schema: A locally resolved module with all the
      imported references resolved as well and with non data definition
      statements removed.

3.  Schema representations

   The YANG language defines several statements that act as syntactic
   abstraction and need to be processed before a YANG module can be used
   for handling YANG instance data.  For example, a “uses” statement is
   replaced by all the substatements of a referenced “grouping”
   statement or a “typedef” statement can be linked to other “type”
   statements.  The referenced statements can be local (defined in the
   same module, or included submodule) but also foreign (defined in
   another imported module).

3.1.  Locally resolved module (single module)

   This representation of a YANG module includes all submodules of the
   main module but resolves only statements that reference other
   statements found in the same module.  No references to imported
   modules (that are using an imported prefix) are resolved.

   For example, any changes of a referenced “typedef” or “grouping”
   defined in an imported module would not affect the locally resolved
   module and are out of scope for this representation.

   All the rules for classifying individual statement changes mentioned
   in Section 4.2 apply to this module representation.

3.1.1.  Deviation

   Regardless of whether the “deviation” target node is local in the
   same module or in an imported module, it is never resolved and
   applied.  Instead, the “deviation” statement with all its
   substatements is kept in the locally resolved module so that it can
   be considered in the schema comparison algorithm.

3.1.2.  Refine

   The “refine” statement is processed differently based on whether the
   affected “grouping” is defined in an imported module or the local
   YANG module.  In the former case, when the relevant grouping is
   imported, the “refine” is not resolved and kept in the module.  And
   then examined in the comparison algorithm, similarly to the
   “deviation” statement.



Vaško, et al.             Expires 25 April 2027                 [Page 4]

Internet-Draft           YANG Schema Comparison             October 2026


   However, all the “refine” statements targeting a local “grouping” are
   applied on the nodes of the grouping when the “uses” is resolved.
   After processing the “refine” statements with all its substatements,
   they are effectively removed from the locally resolved module to
   avoid reporting changes of any “refine” statements twice.

3.1.3.  Augment

   All the “augment” statements are processed similarly to “refine”
   statements.  Meaning that augments of imported groupings are not
   resolved and compared directly while augments of local groupings are
   applied and then removed from the module.

3.2.  Fully resolved schema (set of modules)

   The fully resolved schema representation consists of one or more YANG
   modules.  Each of these is fully resolved according to the rules of
   the YANG language meaning that every referenced statement, including
   to other imported modules, is resolved, unlike locally resolved
   modules.  The result is one large tree with schema nodes of all the
   YANG modules.  The comparison algorithm MAY then choose to compare
   top-level schema node subtrees belonging only to a single YANG
   module.

   Next, all the statements used only for syntactic abstraction that do
   not affect YANG instance data are removed.  Note that the
   “description” or “units” statements are kept because they may
   influence the data.  Also, “error-app-tag” and “error-message”
   statements remain in the fully resolved schema for applications to
   learn that the generated error information has changed.

   The steps taken when fully resolving a module include:

   *  All submodules of a single module are merged to create one large
      YANG module.

   *  "Import" statements are resolved by finding the referenced YANG
      modules and making their contents available.

   *  "Uses" statements are replaced by the referenced "groupings" and
      the YANG nodes they define.  Any “when” statement of the “uses” is
      moved down to all the direct descendant schema nodes of the
      “grouping”.

   *  Types referencing any "typedef" statements are replaced with the
      actual type details.





Vaško, et al.             Expires 25 April 2027                 [Page 5]

Internet-Draft           YANG Schema Comparison             October 2026


   *  Augments are resolved by placing the included YANG nodes in their
      targets.  Any “when” statement of the “augment” is moved down to
      all the direct descendant schema nodes of the “augment”.

   *  "Deviation" and "refine" statements are applied by changing the
      appropriate schema nodes.

   *  All the "if-feature" statements are evaluated based on the enabled
      "features" of implemented YANG modules and the disabled schema
      nodes are removed.

   *  All the extension-instances have a matching “extension” defintion.

   After the resolution, the following statements are completely removed
   with their substatements:

   *  organization

   *  contact

   *  reference

   *  import

   *  include

   *  revision

   *  typedef

   *  grouping

   *  augment

   *  deviation

   *  feature

   *  if-feature

   *  refine

   *  extension

   Also, these schema nodes are removed but replaced with their schema
   node substatements:

   *  choice



Vaško, et al.             Expires 25 April 2027                 [Page 6]

Internet-Draft           YANG Schema Comparison             October 2026


   *  case

   The term “schema” was chosen instead of “module” on purpose because
   when statements are imported from external modules, the resulting
   schema then includes statements from several YANG modules.  But the
   fully resolved schema representation of a module always includes only
   the top-level schema node trees of that module.

   Only a subset of the module update rules in Section 4.2 apply for the
   fully resolved schema.  Specifically, the rules for removed
   statements cannot be applied but other present statements are
   processed normally.

   How the concrete set of YANG modules of a fully resolved schema is
   described is out of scope of this document.  But suitable existing
   structures include YANG data of “ietf-yang-library” from [RFC8525] or
   “ietf-yang-package-instance” in [I-D.ietf-netmod-yang-packages].

3.3.  Choosing a schema representation

   Selecting a suitable schema representation for the comparison
   algorithm depends on the desired purpose.  But for a complete set of
   changes, both the representations should be compared and their output
   merged to get the combined output of the two comparisons.

   YANG module authors will primarily be interested in the locally
   resolved module representation.  Using it for the comparison
   algorithm will yield all the changes that occurred in the specific
   YANG module only while ignoring any possible changes in imported
   modules.  This information can then directly be used to decide the
   correct semantic version of the new revision of this module.  The
   rules for selecting versions are defined in
   [I-D.ietf-netmod-yang-semver].

   Any YANG-based application handling YANG instance data always uses
   the fully resolved schema representation.  So, when running the
   schema comparison algorithm with the intent of learning the changes
   in the corresponding valid YANG instance data of the module, this
   representation should be used.  With some additional information, the
   output of this comparison can then also be used to transform valid
   data of the old schema revision to data valid for the new schema
   revision.  All these tools and applications are typically clients or
   servers of YANG-driven protocols, e.g. NETCONF, RESTCONF, or gRPC.

3.3.1.  Examples

   To illustrate the different output of the comparison algorithm each
   schema representation can generate for the same YANG module changes,
   following are a few examples.

   When a “typedef” or “grouping” name changes, the algorithm for
   locally resolved module will detect the change and report it as non-
   backwards-compatible.  This is useful especially when importing such
   a module to learn that any references to the original statements will
   no longer be valid.  However, if using the fully resolved schema,
   this difference will not be detected at all since it does not affect
   YANG instance data corresponding to this module.

   Another specific use-case is when a module with “uses” that
   referenced an external “grouping” replaces that “uses” node directly
   with schema nodes in the “grouping” effectively resolving the “uses”
   similarly to a YANG module parser.  Such a change is non-backwards-
   compatible based on the YANG 1.1 updating rules and reported that way
   when using a locally resolved module.  But the fully resolved schemas
   will be completely the same before and after the change so the
   comparison algorithm will not generate any changes and report full
   compatibility of the old and the new modules with their instance
   data.

4.  Comparison algorithm

   This algorithm is defined for individual locally resolved modules and
   fully resolved schemas.  All the statements are compared with their
   content, recursively, in the old revision and the new revision of the
   module or schema.  Depth-first search order for the statement
   traversal SHOULD be used.

   The non data definition statements are considered modified when their
   content is changed or any of their substatements are changed.  If a
   statement is present in the old revision and missing in the new
   revision, it is considered removed.  Conversely, if missing in the
   old revision but present in the new revision, it is considered added.

   Data definition statements are compared similarly except that a
   change in a descendant data definition statement is not considered a
   change of the parent data definition statement but a separate change
   instead.

   Only statements with any changes are reported and included in the
   comparison algorithm output.

4.1.  Module identification

   When generating the comparison output of two modules, unique
   identification of these modules SHOULD be included.  For both the old
   and the new revision of the base module, its name, revision, list of
   submodules, and a leaf-list of enabled features is included.  For the
   fully resolved schema, the same information is also reported for all
   the imported YANG modules, recursively.  This ensures that if any
   other output is produced with a different set of changes for two
   fully resolved schemas, their identification information must also
   differ.

4.2.  Change conformance

   Every change is classified as editorial, backwards-compatible, or
   non-backwards-compatible.  The classification is based on Section 11
   of [RFC7950] which mentions most of the possible changes between two
   revisions of a YANG 1.1 module and Section 3.1 of
   [I-D.ietf-netmod-yang-module-versioning] adds more details about the
   exact conformance of statements with various "status" statement
   values.  Finally, [I-D.ietf-netmod-yang-semver] defines what
   classifies as an editorial change.

   General non-normative explanation of change conformance
   classification can be found in Appendix B.

4.2.1.  Deviations, Refines, and Augments

   All the statement change conformance follows the general rules above
   if these statements are present in the schema representation, see
   Section 3.  But this clarification is added to make certain that the
   rules are interpreted correctly.

   Since “deviation” and “refine” statements are not among the allowed
   statements that can be changed when updating a module in Section 11
   of [RFC7950], any non-editorial change of these statements or their
   substatements is treated as non-backwards-compatible.

   But since “augment” statements can only add schema nodes, these can
   be processed and compared normally.











Vaško, et al.             Expires 25 April 2027                 [Page 9]

Internet-Draft           YANG Schema Comparison             October 2026


   So, for example, even if removing the “mandatory” statement is
   considered backwards-compatible, a new “deviation” removing the
   “mandatory” statement from its target node is considered a non-
   backwards-compatible change.  Similarly a “refine” of the
   “description” of a node is classified as non-backward-compatible
   change.  However, a change in the “description” of a “deviation”
   statement is treated as a standard “description” change because it
   describes the “deviation” statement itself and does not affect the
   deviation target node.

4.2.2.  Conformance extensions

   There are cases when it may be impossible for tooling to accurately
   determine the conformance of a change but a default conformance is
   always assumed for every statement.  The affected ambiguous
   statements with their default conformances are:

   *  pattern - NBC

   *  when - NBC

   *  must - NBC

   *  description - Editorial

   *  reference - Editorial

   *  presence - Editorial

   *  extension instance - BC

   Normally, any modification of these statements is reported with the
   default change conformance.  However, if the author of the new
   revision of a YANG module determines that the change of one of the
   aforementioned statements has a different conformance based on the
   compatibility rules for the specific statement, they can decide to
   use the special extension instances to signify this fact.  These are:

   *  ed-change-at SEMVER

   *  bc-change-at SEMVER

   *  nbc-change-at SEMVER

   They determine the conformance of the change of the marked statement
   to be editorial, backwards-compatible, or non-backwards-compatible,
   respectively.  The argument is a semantic version of the YANG module
   revision that introduced the specific change and these extension



Vaško, et al.             Expires 25 April 2027                [Page 10]

Internet-Draft           YANG Schema Comparison             October 2026


   instances are sticky, meaning they remain in the module even in its
   later revisions.  Also, a YANG statement can have multiple
   conformance extension statements.  For example, when a pattern
   changes in multiple versions of a module, each change can be marked
   with an extension to explicitly state the conformance of the change.

4.3.  Algorithm variants support

   Tools implementing schema comparison SHOULD support comparing locally
   resolved modules, fully resolved schemas, and both representations
   together.  In case the comparison generates YANG data for the "ietf-
   yang-schema-comparison-output" YANG module, simple XPath filters can
   be used to select any subset of changes.

   Data definition statements are present in both the locally resolved
   module and fully resolved schema.  So if both representations are
   compared normally, there would be duplicate changes reported in the
   algorithm output.  These duplicate changes MUST be avoided and
   filtered out.

   The YANG modules specified in this document define extensions ("ietf-
   yang-schema-comparison") and a schema for data ("ietf-yang-schema-
   comparison-output") that are designed to be used by offline tooling
   to generate output describing the differences between two supplied
   YANG modules.

   The YANG module specified in this document MAY be accessed via
   network management protocols such as NETCONF [RFC6241] or RESTCONF
   [RFC8040].  The lowest NETCONF layer is the secure transport layer,
   and the mandatory-to-implement secure transport is Secure Shell (SSH)
   [RFC6242].  The lowest RESTCONF layer is HTTPS, and the mandatory-to-
   implement secure transport is TLS [RFC8446].

   The Network Configuration Access Control Model (NACM) [RFC8341]
   provides the means to restrict access for particular NETCONF or
   RESTCONF users to a preconfigured subset of all available NETCONF or
   RESTCONF protocol operations and content.

   When the module is used by offline tooling, there are no security
   considerations, since the user has full access to all YANG modules
   being used.

   The "schema-comparison" structure defined in the "ietf-yang-schema-
   comparison-output" module contains all the groupings reflecting the
   changes between YANG modules.  If instances of this structure are
   generated or published by online tooling, care needs to be taken so
   that information about non-public YANG modules is not inadvertently
   disclosed.

   Since the module does not define any RPCs, actions, or notifications,
   the security considerations for such statements are not provided
   here.

Appendix A.  Schema Comparison Algorithm Output YANG Module

   This YANG module defines the specific output of the schema comparison
   algorithm, supporting comparison of the locally resolved module,
   fully resolved schema, or both.  The "ietf-yang-schema-comparison-
   output" YANG module imports definitions from the "ietf-yang-types"
   module defined in [RFC6991], the "ietf-yang-library" module defined
   in [RFC8525], and the "ietf-yang-structure-ext" module defined in
   [RFC8791].

   Generating schema comparison data in the form of YANG instance data
   compliant with this YANG module is optional but makes it easier for
   further automatic processing by tools and also allows for simple
   filtering of the data.





Vaško, et al.             Expires 25 April 2027                [Page 18]

Internet-Draft           YANG Schema Comparison             October 2026


   Non data definition statements are uniquely identified with their
   YANG identifier and data definition statements with their absolute
   schema node-ids.  For every change, the changed statement and the
   parent of the changed statement are included.  While redundant in
   many cases, it allows the algorithm to uniquely report changes in
   nested statements, e.g. an extension instance change in the type of a
   leaf statement.  Also, all the unchanged substatements with their
   value or content are included for every changed statement, for both
   the older and the newer revision of the YANG module, if applicable.
   This ensures that the output includes all the possibly required
   information without relying on learning it from the YANG modules
   themselves.

Appendix B.  Change Conformance Principles

   This appendix clarifies the general principles based on which
   statement changes are categorized.  They are not meant to replace any
   specification but rather help with understanding it.

B.1.  Editorial change

   An editorial change does not affect valid YANG data of the semantics
   of the YANG module in any way.  That is, it does not make the valid
   data value space smaller or larger and it must remain exactly the
   same as in the module revision without the change.  Also, for a
   change to be editorial, it must not affect any YANG module importing
   the changed YANG module.

   In addition to obvious editorial changes such as fixing a typo in a
   "description", changing the local "prefix" of the module is also
   categorized as editorial because it does not affect importing
   modules.  Or, replacing a "uses" statement directly with the nodes in
   the referenced "grouping" without any other changes.








Vaško, et al.             Expires 25 April 2027                [Page 75]

Internet-Draft           YANG Schema Comparison             October 2026


B.2.  Backwards-compatible change

   For a change to be backwards-compatible, it has to expand the value
   space of valid YANG data.  That is, all the valid YANG data nodes and
   values before the change must remain valid but additional nodes or
   values can also become valid after the change.  Also, backwards-
   compatible changes may influence importing modules but must not cause
   them to become invalid.  In other words, they may expose new
   statements whose removal would then be considered a non-backwards-
   compatible change but generally must not change the already exposed
   statements.

   For some examples, the majority of possible backwards-compatible
   changes are specifically mentioned directly in Section 11 of
   [RFC7950].

B.3.  Non-backwards-compatible change

   If a change is not editorial nor backwards-compatible, it is then
   categorized as non-backwards-compatible.  Such changes shrink the
   value space of valid YANG data, causing some previously valid nodes
   or values to no longer be valid.  Also, any change that may cause an
   importing module to become invalid according to the YANG
   specification must be non-backwards-compatible.

   Examples of less common or less obvious compatibility-breaking
   changes are changing the "yang-version" of a YANG module or expanding
   the size of a "type".  The former change may break importing modules
   because of specific rules defined for the "import" statement and the
   target module's YANG version.  Changing a "type" of a leaf from
   "uint32" to "uint64" may seem to fit the definition of a backwards-
   compatible change, but it may not be so for some data encodings that
   use a fixed binary data chunk (which would grow in size) or even a
   text format that may use a different encoding for the two types.
   Specifically, the JSON YANG data format [RFC7951] encodes a "uint32"
   value as a JSON number but a "uint64" as a JSON string.
